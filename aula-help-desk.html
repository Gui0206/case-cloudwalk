Projetando um help desk multimarca

Como Ana recebe o primeiro chamado?

Objetivo desta etapa Fazer o relato chegar a alguém que possa responder.

Uma lojista da InfinitePay escreve “meu repasse não caiu”. Comecemos com a lojista e Ana online ao mesmo tempo. O que a aplicação precisa fazer para as duas conseguirem conversar?

A lojista envia o relato pelo navegador. A API, a parte do servidor que recebe os pedidos, abre um chamado. Ana o consulta e pergunta pelo identificador da venda. A lojista responde VENDA-42. Esse é o primeiro atendimento que nosso desenho consegue explicar.

O que o case pede

O TAPI prevê duas marcas, três canais simulados (chat, WhatsApp e e-mail), triagem por agente e transferência com histórico para uma equipe. A operação precisa configurar as filas e poder reconstruir cada decisão. Neste projeto o agente é simulado. Os primeiros desenhos isolam decisões de projeto; as medições nas etapas 8 e 9 vêm de execuções reais do protótipo.

O que Ana encontra se o servidor reiniciar?

Objetivo desta etapa Reabrir o mesmo chamado amanhã com as duas falas na ordem certa.

A conversa já funciona enquanto a aplicação está rodando. Se as falas vivem apenas na memória do processo, reiniciá-lo apaga tanto o relato quanto VENDA-42. Como relacionar as duas mensagens depois?

A API em Go grava uma linha para o chamado e uma linha por fala no PostgreSQL, um banco que conserva os registros após o reinício. As falas carregam o mesmo identificador de chamado. Quando Ana volta, a API usa esse vínculo para reconstruir a conversa. VENDA-42 identifica a venda que ela vai investigar.

Em uma abertura, o navegador faz um pedido HTTP POST /api/tickets. A resposta entrega o identificador do chamado. Assim a loja pode fechar o chat e voltar à mesma conversa. Ainda dependemos de Ana para fazer cada primeira pergunta.

Ana precisa pedir a referência de toda venda?

Objetivo desta etapa Liberar Ana para investigar os casos que precisam dela.

Toda investigação começa pela mesma informação. Se a loja ainda não informou a referência, alguém precisa pedi-la. Experimente o desenho mais simples: a API salva o relato e chama diretamente um programa que lê o histórico e faz a primeira pergunta.

Nesse desenho inicial, a API aguarda a resposta do agente e a devolve ao chat. Com o agente disponível e rápido, isso já resolve a triagem. Agora imagine que a API reinicia logo depois de salvar o relato e antes de fazer a chamada. O que faria esse caso voltar à triagem?

Como descobrir o que ainda falta enviar?

Objetivo desta etapa Recuperar a obrigação de entrega após um reinício.

O histórico diz que a lojista escreveu. A mesma fala estaria lá tanto se a chamada já tivesse acontecido quanto se ainda faltasse fazê-la. Precisamos registrar essa diferença.

A API grava a fala e um registro “enviar este pedido” na mesma transação. O PostgreSQL confirma ambos juntos ou desfaz ambos. A tabela desses envios chama-se outbox. Neste desenho intermediário a API ainda tenta enviar logo após salvar. Se cair antes, a obrigação continua pendente. Quem vai buscá-la quando a loja já tiver fechado o chat?

Quem tenta de novo quando ninguém está usando o chat?

Objetivo desta etapa Confirmar a abertura para a loja e continuar tentando a entrega em segundo plano.

A própria API poderia chamar o destino durante a abertura. Se ele demorar, a lojista espera. Se o envio falhar depois da gravação e ninguém fizer outro pedido, a linha pode ficar parada. Precisamos de alguém que acorde por conta própria.

O worker é um processo que procura envios pendentes, reserva um, tenta entregá-lo e registra o resultado. Se falhar, agenda outra tentativa. A API pode devolver o número do chamado assim que a transação termina. O mesmo papel poderia rodar dentro do servidor; no projeto ele roda separadamente. Por enquanto, imagine o worker chamando o agente diretamente.

O agente precisa estar online para receber trabalho?

Objetivo desta etapa Entregar um pedido para processamento mesmo durante uma pausa do agente.

Com a outbox e o worker, o sistema já consegue esperar e tentar de novo. Se o agente for o único destino, esse desenho é viável. Agora queremos que o help desk conclua a entrega e que o agente controle quando e em que ritmo vai ler os pedidos, sem consultar o banco do help desk.

Introduzimos um broker, serviço que recebe mensagens de quem produz e as disponibiliza para quem consome. Aqui, Redpanda guarda os pedidos em um fluxo nomeado, o tópico desk.requests. O worker poderia publicar diretamente usando o protocolo Kafka, como no desenho. Após a publicação confirmada, o pedido pode aguardar no broker até o agente voltar. Durante um pico essa espera pode crescer.

Se o worker já poderia publicar, por que colocar uma ponte?

Objetivo desta etapa Permitir que o help desk entregue por HTTP a uma integração que usa Kafka.

Na figura anterior o worker precisava conhecer o protocolo Kafka, o endereço do broker e o tópico de pedidos. Isso funciona quando se controla o produtor. No case, a interface de integração do help desk é um webhook: ele deve conseguir avisar outro serviço fazendo uma chamada HTTP. O broker do projeto recebe publicações pelo protocolo Kafka.

A ponte oferece POST /webhook, recebe o evento HTTP e o publica em desk.requests. Só confirma o sucesso ao worker depois de publicar. Se a ponte ou o broker falhar, o envio continua sujeito a nova tentativa. Ganhamos um ponto onde adaptar os protocolos; pagamos uma chamada e um processo a mais. O worker continua necessário para retomar envios pendentes, inclusive quando a ponte é o destino.

Onde aparece a pergunta que o agente acabou de fazer?

Objetivo desta etapa Levar a resposta ao mesmo chamado mesmo que a abertura já tenha terminado.

A loja já recebeu o número do chamado. A chamada HTTP de envio também já terminou. O agente lê o pedido agora e produz “qual é a referência da venda?”. Em qual conexão ele devolveria essa pergunta?

Usamos um segundo tópico, desk.responses. O agente publica a resposta com a identificação do caso. A ponte lê esse fluxo e chama a API por HTTP para gravar a fala. A conversa volta a ficar disponível no chat. Uma partição é uma sequência ordenada dentro do tópico. A posição de uma mensagem nessa sequência chama-se offset. A ponte confirma até onde leu depois de processar o retorno.

E se a pergunta sobre a venda chegar duas vezes?

Objetivo desta etapa Permitir uma nova tentativa de entrega sem duplicar a fala no chat.

A ponte entregou a pergunta e a API a salvou. A ponte cai antes de confirmar ao broker até onde leu. Quando voltar, poderá receber a mesma resposta. Confirmar a leitura antes de salvar também seria arriscado: uma queda nesse intervalo faria a pergunta desaparecer.

A API guarda o ID do retorno na inbox, a tabela de eventos recebidos, junto com a fala em uma transação. Na segunda entrega, o mesmo ID já existe. A lojista vê uma pergunta e pode responder VENDA-42. Repetir uma operação e conservar o mesmo efeito é idempotência.

Agora troque a falha. Um retorno inédito chega tarde e o chamado já está com um analista. Ter um ID novo basta? A API confere também a fase, o estado e a revisão. Se o evento se refere a um estado ultrapassado, registra a ocorrência e preserva o atendimento atual.

Uma falha transitória pode desaparecer com uma nova tentativa. O worker aumenta o intervalo entre tentativas até 30 s e registra a falha definitiva após dez tentativas malsucedidas. Na integração Kafka, falhas repetidas de processamento podem ir para desk.failed, um tópico para inspeção. Os scripts de recuperação permitem inspecionar e reenviar preservando o ID original. Mensagens problemáticas continuam visíveis à operação.

Quem investiga quando o agente termina a triagem?

Objetivo desta etapa Entregar VENDA-42 à equipe responsável com as falas já coletadas.

Uma lista única de casos aguardando funcionaria se todos os analistas atendessem todos os clientes. Agora temos duas marcas. Os especialistas de repasses da InfinitePay devem ver o caso brasileiro; o suporte da JIM precisa continuar recebendo seus próprios casos.

A API usa a primeira regra compatível com os dados do caso e grava fila, equipe, motivo e versão. A fila humana é uma consulta aos casos que aguardam aquela equipe no PostgreSQL. Diferentemente do leitor de um tópico, Ana precisa escolher trabalho por permissão, prioridade e estado atual. A operação consegue editar os destinos. O que aconteceria se esquecesse de preencher a marca?

Quem deve investigar o repasse de cada marca?

Objetivo desta etapa Encaminhar repasses da InfinitePay aos especialistas e preservar o atendimento da JIM.

O agente coletou VENDA-42 e pediu ajuda humana. Uma regra que diz apenas “repasse vai para Repasses BR” parece suficiente até uma lojista da JIM escrever a mesma frase. Como a operação percebe esse desvio antes de publicar?

A fila humana reúne os casos disponíveis para uma equipe. O motor escolhe o destino pela primeira regra compatível. O simulador executa esse mesmo motor com a configuração publicada e com o rascunho. Compare os destinos abaixo e depois troque o filtro da regra.

Antes de publicar, experimente retirar o filtro de marca. Quem passaria a receber os clientes da JIM?

Prévia da regra de repasses JIM → Suporte EUA · 3 de 48 destinos mudam.

O simulador executa o mesmo motor duas vezes para cada cenário, primeiro com a versão publicada e depois com o rascunho. São 2 marcas × 4 assuntos × 2 etapas × 3 prioridades, totalizando 48 combinações. Uma função pura recebe configuração e dados, devolve o destino e deixa o banco intacto. Assim a prévia pode mostrar regra vencedora, fila e equipe sem criar 48 chamados.

A publicação exige a versão de origem e a assinatura do rascunho simulado, um resumo calculado a partir do conteúdo. Se alguém mudar a base ou alterar o texto da política, a aplicação exige uma prévia atualizada. A nova versão vale para decisões futuras. A auditoria conserva qual versão produziu cada decisão anterior.

Como testar o próprio simulador? Se o código compartilhado tiver um erro, simulação e execução podem concordar no destino errado. Por isso o teste define destinos esperados de maneira independente. Abre 24 conversas em três canais e confere 48 decisões reais. No painel, dois casos com as mesmas falas mostram o efeito isolado da marca. Conferir a previsão e as conversas gravadas.

Como dar trabalho a Ana e Bruno ao mesmo tempo?

Objetivo desta etapa Atribuir um caso livre a cada analista, respeitando equipe e prioridade.

Os casos 42 e 43 estão livres. Ana e Bruno carregam a lista e clicam no 42. O banco protege o responsável, mas Bruno recebe um conflito HTTP 409 e precisa tentar de novo. Por que deixar o navegador escolher um ID que pode já ter mudado de dono?

O botão passa a pedir Assumir próximo caso. A API escolhe e reserva o caso dentro da mesma transação. Se Ana estiver reservando o 42, o banco pode pular essa linha e entregar o 43 a Bruno. A escolha considera apenas o trabalho que cada analista está autorizado a assumir.

O botão Assumir próximo caso passou a delegar a escolha ao servidor. A API considera apenas casos humanos aguardando, sem dono, da marca e equipe da sessão e da fila selecionada, quando houver filtro. O trecho abaixo mostra a lógica de seleção em SQL simplificado.

SELECT id FROM tickets
WHERE phase = 'Humano' AND status = 'Aguardando analista'
  AND owner IS NULL AND brand = $1 AND team = $2
  AND ($3 = '' OR queue = $3)
ORDER BY CASE priority WHEN 'Urgente' THEN 1
                       WHEN 'Alta' THEN 2 ELSE 3 END, updated, id
LIMIT 1 FOR UPDATE SKIP LOCKED;

$1, $2 e $3 recebem marca, equipe e filtro. ORDER BY ordena por prioridade, depois por atualização mais antiga e por ID para desempatar. LIMIT 1 escolhe uma linha. FOR UPDATE a bloqueia durante a transação. SKIP LOCKED deixa Bruno avançar se Ana já reservou essa linha. A API escreve responsável, estado Em atendimento e auditoria antes de confirmar e liberar o bloqueio. Se não houver candidato livre, a resposta indica fila vazia. A prioridade vale entre os chamados elegíveis disponíveis naquele instante.

Ana abre a conversa com o resumo e a referência VENDA-42, responde e pode encerrá-la. O banco registra o encerramento e o histórico segue consultável. Para verificar a implementação, acompanhe a seleção e a atribuição no backend Go.

Dois urgentes chegam juntos. Quem será atendido primeiro?

Entre casos elegíveis e livres, a consulta usa atualização e depois ID para desempatar. Caso um já esteja bloqueado, o próximo analista pode avançar para outro elegível. Ordem de seleção também não garante ordem de conclusão do atendimento.

O que significa aguentar 400 aberturas por segundo?

Objetivo desta etapa Descobrir se a loja recebe a primeira resposta durante o pico.

Uma confirmação de abertura rápida pode esconder uma fila crescendo depois da API. Medimos dois intervalos: do pedido ao aceite e da abertura até a primeira fala do agente gravada.

A 400/s, o p95 do aceite foi 14 ms; o da primeira resposta chegou a 14,252 s. O p95 é o tempo dentro do qual terminaram 95% das observações. Para localizar a espera, contamos o trabalho acumulado em cada passagem do mapa.

Do pico curto ao primeiro limite

O primeiro ensaio enviou 120 conversas em lotes de 12 e verificou uma resposta por caso. O worker em Go foi comparado com 1, 4, 8 e 16 goroutines, tarefas que a linguagem executa concorrentemente. A mudança também retirou uma pausa fixa de 70 ms após cada sucesso. Isso impede atribuir o ganho apenas à linguagem. A configuração usual ficou com quatro tarefas no dispatcher, o processo que busca e entrega eventos.

No teste sustentado, o gerador agendou novas aberturas pelo relógio. Se esperasse uma resposta antes de enviar a próxima, o próprio teste reduziria a carga quando o serviço ficasse lento. Subimos por 10, 25, 50, 100, 200 e 400 aberturas/s. A 200/s, o p95 da resposta ficou em 75 ms. A 400/s, o p95 de abertura ainda era 14 ms, mas havia 5.695 casos esperando resposta quando as chegadas pararam.

Por que limitar conexões se queremos atender mais clientes?

Objetivo desta etapa Manter o PostgreSQL acessível durante o pico.

O banco registrou 127 erros por excesso de conexões. Abrir mais uma conexão para cada chamada concorrente acabava esgotando o recurso usado por todas elas.

Um pool reutiliza conexões. Ao atingir o limite, a próxima operação espera uma conexão livre. Isso custa espera na API, mas impede que ela abra conexões sem limite no banco. Limitamos a API a 32. A ponte também passou a reutilizar a conexão HTTP de retorno. Na rodada com um leitor, o p95 da primeira resposta ainda foi de 4,959 s. Para entender o restante, examinamos onde os retornos se acumulavam.

Como a ponte pode ler mais respostas ao mesmo tempo?

Objetivo desta etapa Processar em paralelo respostas que já estão disponíveis.

O agente acompanhava a entrada, mas havia respostas publicadas que a ponte ainda não havia terminado de processar. O tópico já tinha três partições. Um leitor processando as entregas em sequência podia deixar trabalho pronto aguardando.

Usamos três leitores no grupo da ponte, um por partição naquela configuração. O p95 passou a 3,038 s. Quando as chegadas pararam, 1.184 dos 1.185 casos sem resposta ainda estavam na outbox. Aumentar os leitores outra vez não adiantaria para um pedido que sequer chegou ao broker.

Por que o worker demora para achar um envio pronto?

Objetivo desta etapa Localizar rapidamente a próxima linha pendente da outbox.

A tabela conserva muitos envios concluídos. O plano de execução mostrou que o banco percorria a tabela e ordenava linhas para selecionar um único pendente. O agente podia estar disponível durante toda essa busca.

Um índice parcial mantém uma estrutura de busca só para os pendentes, já ordenados por horário de envio e ID. O banco mantém essa estrutura a cada mudança de estado. Na rodada seguinte, o p95 da primeira resposta foi de 75 ms. Os ensaios ocorreram em sequência com históricos diferentes; o gráfico mostra os valores observados.

Medições por rodada

O que o teste de primeira resposta deixou de exercitar?

Objetivo desta etapa Descobrir se cliente e analista conseguem terminar a conversa durante cinco minutos de pico.

A primeira pergunta do agente chegou. Ainda faltam a segunda mensagem, a transferência, a leitura do histórico e a tomada do caso. Mantivemos 400 novas conversas/s e acrescentamos esses passos.

A primeira rodada mista aceitou 119.659 aberturas. Alguns analistas viam a lista vazia enquanto milhares aguardavam: a consulta cortava a lista antes de selecionar os casos ativos. Filtrar ativos antes de limitar a página fez a fila exibir trabalho disponível.

Passamos para cinco minutos com 128 sessões de cliente, 96 tarefas acompanhando conversas, duas mensagens por cliente e 16 analistas simulados. A API aceitou 119.659 aberturas no primeiro ensaio misto. No corte, o consumidor de respostas tinha 56.764 eventos sem confirmação de posição. Havia também um defeito de consulta: os 250 primeiros casos visíveis podiam estar todos encerrados, enquanto milhares aguardavam abaixo do limite.

Por que a ponte continua esperando depois da correção da fila?

Objetivo desta etapa Liberar capacidade de banco para gravar as respostas.

Enquanto aguardavam, os clientes releram o histórico inteiro 1,66 milhão de vezes em uma rodada. Cada releitura disputava recursos com a gravação que faria a tela mudar.

O navegador passou a consultar um estado pequeno e a buscar o histórico completo quando há mudança. Quando nada muda, as consultas ficam mais espaçadas. Ao detectar uma mudança, o chat busca as falas novas no histórico.

Como dar passagem às respostas da ponte?

Objetivo desta etapa Gravar uma resposta mesmo quando há muitos clientes consultando o chat.

Cada retorno precisa de uma conexão para gravar. Se os clientes ocupam todas, a resposta pronta espera e o cliente continua consultando. Como reservar espaço para a operação que destrava a conversa?

Reservamos oito conexões para retornos. Para reduzir o tempo ocupado por cada gravação, a API agrupou mensagem, auditoria e atualização do caso em uma instrução SQL. Na ponte, as confirmações de posição passaram a ser agrupadas a cada 100 ms. Uma queda nesse intervalo pode repetir uma entrega já gravada; a inbox reconhece seu ID. As rodadas mediram essas mudanças em conjunto com as leituras menores do chat.

Se 119.857 conversas terminaram, onde estão as outras 143?

Objetivo desta etapa Verificar que as 120 mil chegadas programadas realmente aconteceram.

A meta de 400 aberturas/s durante 300 segundos dá 120 mil. Um gerador com limite de aberturas simultâneas pode pular um disparo quando seus próprios recursos estão ocupados. Um servidor saudável nunca verá essa chegada.

Contamos programadas, emitidas e encerradas. Ao elevar o limite do gerador, as 120 mil conversas foram emitidas e encerradas. O p95 das duas respostas ficou em 119 ms e a drenagem levou mais 1,74 s após o fim da entrada.

Essas rodadas mudaram juntas as leituras, as escritas e as confirmações. Os números medem o conjunto. Primeira carga mista · Primeira correção · Otimização e confirmação.

As 120 mil conversas chegaram ao fim?

Objetivo desta etapa Verificar o fluxo inteiro com cinco minutos de chegadas, analistas simultâneos e seis meses de histórico sintético.

A primeira resposta é só o começo. A 400 aberturas/s por 300 segundos, esperamos 120 mil conversas. Cada cliente envia duas mensagens e um em cada cinco pede um humano. Se o gerador pular chegadas, ou a ponte acumular retornos, a taxa anunciada pode parecer boa mesmo com trabalho faltando.

Conferimos os dois lados: quantas chegadas foram programadas e quantos casos terminaram. Na rodada final com histórico, as 120 mil conversas encerraram. A auditoria registrou uma atribuição para cada um dos 24 mil casos humanos e os 240 mil eventos novos tiveram confirmação após a drenagem.

Quanto o histórico pesa na fila?

Carregamos 360.000 chamados encerrados, distribuídos por 180 dias sintéticos. São 1.512.000 mensagens, 864.000 registros de auditoria e 720.000 eventos anteriores já confirmados. Repetimos a carga de cinco minutos com três prioridades igualmente representadas entre os casos humanos. Isso permite perguntar quanto tempo o cliente espera até ser assumido, incluindo descoberta, consulta e concorrência.

O pedido sobrevive à pausa do agente sob carga?

Objetivo desta etapa Verificar na prática a promessa que justificou introduzir o broker.

Uma fila drenada ao final de um teste saudável diz pouco sobre reinícios. Em um ensaio separado, variamos marcas, canais, assuntos e duração das conversas e desligamos o agente durante o pico.

Durante a interrupção entraram 255 casos que ficaram sem primeira resposta. Ao verificar depois do reinício, os 255 já tinham resposta. Aqui aparece a consequência do desenho da etapa do broker: a publicação e a leitura puderam acontecer em instantes diferentes.

Desligar o agente durante um pico

O ensaio de 400/s reutilizava sessões e se concentrava em Pix. Outro ensaio abriu 6.160 conversas com clientes distintos, quatro assuntos e de uma a cinco mensagens para o agente. Distribuiu um dia sintético em 24 janelas de 15 segundos, com pico de 50 novas conversas/s. Durante a interrupção de 5,10 s do agente, 255 casos entraram e ficaram sem primeira resposta. Na verificação feita 573 ms depois que o comando de reinício retornou, todos já tinham resposta. Esse valor identifica o instante da verificação.

O p95 geral foi 71 ms, enquanto o p99 chegou a 4,27 s. O p99 descreve o limite observado para 99% das respostas e torna mais visível a espera de uma minoria afetada. Houve 3.107 encerramentos automáticos e 3.053 humanos. Experimentos separados também verificaram reentrega e resposta obsoleta após transferência. Perfil e recuperação · Falhas injetadas.

Até onde vale a conclusão?

A infraestrutura medida foi uma máquina com Docker, 12 CPUs e 7,65 GiB para o ambiente de teste, PostgreSQL e Redpanda de nó único. Docker executa os componentes em ambientes separados, chamados contêineres. O Compose registra como iniciá-los juntos e quais dados persistem entre reinícios. A medição sustenta um pico local de cinco minutos com aquele agente, aqueles tempos humanos simulados e aquelas distribuições. Uma rodada por condição oferece pouca informação sobre variabilidade. História de 180 dias inserida no banco mede volume arquivado; disponibilidade contínua por 180 dias exigiria outra observação.

Para dimensionar uma operação real, seriam necessários chegadas por horário e canal, duração de atendimento humano, custo e latência do agente, tamanho das mensagens e um objetivo de serviço. Se o banco único ficar indisponível, a confirmação de abertura também falha. Alta disponibilidade exigiria cópias e um mecanismo testado para assumir o serviço durante a falha. O ensaio de queda do agente mediu uma falha diferente.

Como provar o caminho de VENDA-42 no painel?

Objetivo desta etapa Seguir uma conversa até Ana e verificar que o destino observado coincide com o previsto.

O mapa agora contém dois lugares em que alguém pode estar esperando. Imagine primeiro que o pedido já foi publicado e o agente parou. Depois imagine que o agente terminou a triagem e Ana saiu para almoçar. Onde você procuraria o chamado em cada situação?

Na primeira situação, acompanhe a posição de leitura no tópico de pedidos. Na segunda, procure o caso no PostgreSQL com o estado Aguardando analista. Quando Ana assume, a API registra a atribuição e abre o histórico do mesmo chamado, incluindo VENDA-42. Compare agora as duas marcas no painel.

Reproduza o encaminhamento

Com Docker Desktop em execução, abra iniciar.command na pasta do projeto. O iniciador sobe a aplicação e prepara a configuração local. Para seguir a demonstração, abra o painel do projeto. O código inicial da equipe é demo-local. Use uma instalação de demonstração com as regras iniciais para reproduzir os totais seis e três.

  1. Em Operação, abra Exemplo: repasses. Troque a marca para Qualquer e simule. Encontre uma linha da JIM e leia a regra vencedora. Restrinja a marca à InfinitePay, simule novamente e publique a versão conferida.
  2. Clique em Abrir os dois casos de teste. Abra Conversa e decisão e compare mensagem, resumo, regra e destino. A prévia é hipotética. Este botão cria conversas persistidas pelo caminho completo.
  3. Em Analista, entre como InfinitePay / Repasses, filtre Repasses BR e use Assumir próximo caso. Observe a atribuição no histórico de decisões. Responda e encerre. Com JIM / Atendimento, procure a outra conversa.

O que conferir na demonstração?

A operação consegue experimentar uma regra com casos sintéticos, identificar o efeito em cada marca e conferir, depois de publicar, se duas conversas reais dentro da aplicação chegaram aos destinos previstos.

Como a API recebe o relato da lojista?

{"brand":"InfinitePay", "channel":"Chat",
 "priority":"Normal", "text":"Meu repasse não caiu."}

A API classifica o assunto como Repasse, consulta a configuração ativa e encaminha para a etapa de IA. Gera um identificador para o chamado. As duas mensagens futuras continuam ligadas ao mesmo identificador, ainda que seus textos sejam completamente diferentes.

O que o PostgreSQL guarda?

PostgreSQL é um banco relacional. Cada tabela organiza registros em linhas. Um identificador único permite relacionar a linha do chamado às muitas linhas de mensagens. SQL é a linguagem usada para consultar e modificar essas tabelas.

Uma sessão associa pedidos sucessivos ao mesmo cliente ou perfil de equipe. O navegador apresenta um cookie, um pequeno identificador assinado. A API consulta a sessão e verifica o acesso.
